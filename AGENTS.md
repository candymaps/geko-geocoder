# geko

Multi-country geocoding engine with a tile server (Rust + Planetiler), with data from OSM and official national sources (in Spain: CartoCiudad, Catastro, IGN, INE…). Goal: beat Pelias in speed, coverage and quality, measured with the protocol in PROJECT.md §13.

The full specification (measurable goals, architecture, ports, data contracts, automatic download, search engine, API, measurement and roadmap) is in [PROJECT.md](docs/PROJECT.md). Read it before designing or implementing anything.

The phases are in [PROJECT.md](docs/PROJECT.md), section 15 «Hoja de ruta», and the current state of the project in section 19 «Estado». When a phase is finished, update both.

The items pending review (optimizations, improvements, debt) are in [PROJECT.md](docs/PROJECT.md), section 17 «Pendiente» (generic engine) and, for each country, in its pack's README (`countries/<country>/README.md`, section «Pendiente y decisiones»). Check them before choosing the next step, and delete each item when it is closed (whatever it teaches goes to «Optimizations» in this file or to PROJECT.md).

## Environment

- Building and testing (cargo, `ci/test.sh`) happen in WSL Debian; `geko` runs in Docker (README, «Installation and usage»: the `geko-data` volume is its `/var/lib/geko`). The code lives in each machine's repository folder, which in WSL is `/mnt/<drive>/…`.
- Use `CARGO_TARGET_DIR=$HOME/.cache/geko-target` (outside `/mnt/c`, to build fast).
- On the `D:` machine there is no C compiler in WSL (`build-essential` is missing): Zig is the temporary compiler and linker, with `CC=~/.local/bin/zigcc AR=~/.local/bin/zigar CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_LINKER=~/.local/bin/zigcc`. From PowerShell, run each WSL command from a script (`wsl -d Debian -- bash <script>`): the quotes and `$` of an inline command get mangled on the way.
- Fixed paths: the binary in `/usr/local/bin/geko`, the configuration in `/etc/geko/geko.toml` (with `accept_licenses = true`; `make install` copies `develop/geko.toml`, the configuration of `make start-dev`, the first time; the published image carries none, and geko stops without one; every option is in the README, «Configuration reference») and, beside it, that of each module (`geko-geocoder.toml`: its sources, budgets, cache…) and the data in `/var/lib/geko`. `make install` sets them up with `sudo`. There is no `--config` and no `[data] dir`: only `GEKO_CONFIG` and `GEKO_DATA` change them, for `ci/test.sh` and CI. Country packs are read from `/var/lib/geko/packs/<country>/`, where `geko` downloads those of the scope from `ghcr.io/candymaps/geko/countries/<country>`, or from `GEKO_PACKS`, which is never downloaded; `ci/test.sh` uses the repository's, and `GEKO_PACKS=$PWD/countries make up` tests an unpublished pack. `GEKO_MODULES` (one directory per module, with its `module.toml`) runs a module as a process of its own or loads it as a library (`kind = "process" | "dylib"`) instead of the one linked in, and then a module neither there nor linked in is an error, never a download; `make start-dev` (develop/compose.yaml) builds geko and the modules of its configuration inside Docker and carries them that way; `make modules [MODULE_KIND=dylib]` leaves the geocoder in `$CARGO_TARGET_DIR/modules`, and `GEKO_MODULES=$CARGO_TARGET_DIR/modules ci/test.sh …` checks it that way. Without either, a module not linked in (the image links none) is downloaded into `/var/lib/geko/modules/<module>/<version>/` from `ghcr.io/candymaps/geko-<module>`: the newest of the contract of `geko`, or the one of `[modules.<module>] version` (`registry` changes where from), signed; `geko plan` says which and from where, and `geko purge modules` removes those no active module or kept bundle uses. The private key that signs the packs and the modules is in `~/.config/geko/pack-signing.key` (and in the `GEKO_PACK_SIGNING_KEY` GitHub secret); the public one, in `TRUSTED_KEYS` of `geko-artifact`. Never print it or copy it into the repository.
- Nothing of geko loose in `~`: everything generated goes under `/var/lib/geko` (the Docker volume or, for the golden and `spain` of `ci/test.sh`, the WSL folder), never in the repository: `raw/`, `staging/`, `relocated/`, `canonical/`, `segments/` (work), `bundles/` (published, with `current`) and `golden/<country>` (data of the `ci/test.sh` golden). A/B tests also go in there, and are deleted when done.
- DuckDB CLI in `~/.local/bin/duckdb` (WSL), useful to inspect the staging and canonical Parquet files.
- Always measure performance in `--release`.
- Publishing: the `publish` job of `ci.yml`, after the checks pass on `main`, publishes to ghcr.io the packs that changed and, if the push touches something that goes into it (not only documentation or packs), the modules (`ci/modules.sh`, compiled on the Debian of the image) and the image, which carries no module and is not published unless a module of its contract is, and moves the git tag `sdk-<contract>` if the SDK changed; all with the version in `Cargo.toml` (`<version>-<commit>`). Raising the version in `[workspace.package]` is making a release: in addition, `<version>` on packs and image, `latest` on the image and the git tag `v<version>` on the pushed commit, with its GitHub release.
- GitHub CI (`ci.yml`) only runs on pushes to `main`, or by hand: it checks the deterministic part of what changed and, if it passes, publishes. Other branches are checked locally before pushing: `.githooks/pre-push` runs `make test` (35–50 min; from Windows git, inside WSL) and rejects the push if it fails or if there are uncommitted changes. It is enabled once per clone with `git config core.hooksPath .githooks`; `git push --no-verify` skips it.
- Checks, the same locally and in CI (GitHub only calls the script): `ci/test.sh [--variant …] [--scope …] [--include-performance]`, which only runs tests. `--variant`: `code` (clippy, dependency rules, cargo-deny, features), `contracts` (tests and conformance suites), `results`, `data`, `robustness` and `instructions`; all by default. `--scope`: `es` (the Balearic Islands on frozen data against `countries/es/golden/baseline/`), `lu`, `spain` (all of Spain against the last pushed commit, only locally and on demand: `make test-regression`) and `pelias`; `es,lu` by default. The golden also runs in CI, on pushes to `main`: every country if the push changes the engine (`crates`, `providers`, `languages`…) or `ci/`, only one if only its pack changes. The snapshot, private in `ghcr.io/candymaps/geko/countries/<country>/golden`, is renewed by hand with `make golden-snapshot` (or `golden-snapshot-local`, without publishing), only when the sources have drifted away from it (PROJECT.md §20.1). What each one measures: PROJECT.md §20.
- Valgrind (for the instruction counts of the golden and of Spain) is not installed in WSL: it is extracted in `~/.local/valgrind-deb`, and `ci/test.sh` finds it there on its own. Without valgrind, the instruction counts are an error; `GEKO_BENCH=0` skips them.
- Adding or changing a dependency only rebuilds the stages whose crates use it, directly or indirectly (BACKLOG 31). A common dependency, such as `arrow` or `serde`, still rebuilds almost all of Spain: about 16 min without downloads, with Overture (2026-10-20: staging 7.5 min, merge 3.7, index 4, reverse 0.5). Group those changes before measuring.
- Debugging commands of the geocoder: `geko geocoder parse "<query>"` (interpretations), `geko geocoder query "<query>" [--autocomplete] [--focus lat,lon]` (search with timings) and `geko geocoder reverse <lat> <lon>` (reverse). They require having run `geko build`.

## Branches and commits (Gitflow)

- **Nothing is ever pushed directly to `main`**: no commits, no pushes.
- All new development starts from `dev`, in its own branch with a Gitflow name: `feature/<name>`, `bugfix/<name>`… It ends with a PR from that branch to `dev`.
- A release (a push to `main`) is always a PR from `dev` to `main`.
- All commits follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<optional scope>): <description>`, with type `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci` or `chore`. A breaking change takes `!` after the type (`feat!: …`) or a `BREAKING CHANGE:` footer. The title of each PR follows the same format.

## Key rules

- Selective abstraction: only the ports of PROJECT.md §4 are traits. Everything else is plain code; its trait is extracted when a second real implementation appears.
- No concrete technology (fst, pmtiles, ureq, osmpbf, Planetiler…) is used outside its provider or its crate. `geko-core` only contains domain and traits.
- Traits only expose domain types. Providers are chosen by configuration (`geko.toml`) in `geko-app`, and must pass the conformance suite of their port (`geko-conformance`).
- Multi-country from the start: ISO 3166 codes, `coverage()` per provider, normalizer and parser per country, one index segment per country, `PublicId` with country (`geko:<type>:<country>-<key>`).
- Everything specific to a country lives in its pack, `countries/<country>/` (PROJECT.md §2.4): data, national sources and reference queries (`golden/`). `providers/` only has generic providers. A new country is added by creating its pack, without touching the engine.
  - The pack is data, not code: `geko` reads it at startup (`geko-country-pack`), only for the countries it asks for. Nothing of a country is compiled into the binary: no `#[cfg(feature = "pack-…")]`, no country tables in a generic provider (what a source needs to know about a country goes in the pack's `sources/<source>.toml`), and no national sources as code: they are declared in `sources/<source>.toml` with `kind`, for the generic provider in `providers/` of the kind of service that publishes them; e.g., CartoCiudad has `kind = "ogc-api-features"` because the IDEE serves it through OGC API Features. The `country-pack-<country>` crates only serve the tests.
- Fixed-point coordinates (`Coord`, `i32` in 1e-7 degrees). `f64` only for intermediate calculations.
- Only `geko serve` uses tokio; `plan`, `fetch` and `build` are synchronous (the `Downloader` uses `ureq`).
- Everything is automatic: only what the active modules and the providers enabled for the scope ask for is downloaded and built. Compiled-in sources are used by default if they cover some country of the scope; their `[sources.<id>]` section of `geko-geocoder.toml` is optional and only changes options or disables them. OSM is mandatory: it cannot be disabled. `geko serve` never downloads sources. Downloading requires `accept_licenses = true`.
- Build partitioned by country and region, and incremental by input hash (PROJECT.md §8.3). Each stage leaves a `<dir>.stamp.json` stamp and is skipped if neither its code nor its inputs change; `geko build --force` redoes everything. The build must be deterministic: the cutoff when an output does not change depends on it. A new provider declares in `stage_inputs` which `raw/` files it reads.
- Spain pack (`countries/es/`): CartoCiudad is downloaded through the IDEE's OGC API; the INSPIRE WFS was analyzed and discarded (PROJECT.md §7.6).
- A single source of truth (PROJECT.md §6.5): sources are merged into one master record per entity. Sources are never served separately and duplicates are never allowed; the names from every source are joined as variants. The rules and the street-type dictionary go in each country's pack. The duplicate metrics (§13.6) block the build.
- Inferred attributes (postcode by zones, address of POIs…, PROJECT.md §6.5.4) are always marked as inferred, never mixed with data from a source. The municipality is always assigned by coordinates, never by the name a source brings.
- No download protected by a CAPTCHA or other access control is automated.
- An index of words, not of full names. Addresses are not indexed as documents: they go in compact blocks per street. Local ids in order of importance; early termination within lists, between interpretations and between segments.
- Hot part (pinned in RAM) and cold part (mapped) in separate files.
- geko is a host and its modules (docs/MODULES_PLAN.md): today `geocoder` and `tiles`, enabled by Cargo *feature* and by `[modules]`. The host (`geko-app`, `geko-server`) knows a module only through the contract of `geko-module-sdk` (`Module`): it never depends on the geocoder, and `ci/test.sh` (`architecture`) checks it. Each module serves its routes under `/<module>/`, reads its own `geko-<module>.toml` and builds its own part of the bundle. Every option of a module is documented in its sample file and in its README (`modules/geko-geocoder/`), not in `geko.toml` or the README of the host. A disabled module, layer or country does not download, does not instantiate, does not open files and does not register routes.
- Build and serving on different machines. Bundles are immutable and versioned; a bundle in use is never modified. Production serving on Linux.
- Any change to ranking, normalization or parsing is validated with the reference queries (`countries/<country>/golden/`) and the benchmark. No category of any country may ever get worse compared with Pelias (PROJECT.md §13.2).
  - Locally: `make test-golden-es` and `make test-golden-lu` (or `ci/test.sh`, which runs both), with zero tolerance. It compares hits query by query (also each keystroke), duplicates, calibration, data and bundle size, all deterministic, and CI checks it on every push. Instruction counts are compared with those of the last pushed commit, counted in the same run: the count changes from one processor to another, so an instruction baseline is never stored. Latencies, only with `--include-performance`.
  - If a change improves accuracy, it is accepted as the new baseline with `GEKO_GOLDEN_UPDATE=1`.
  - All of Spain (`make test-regression`: `ci/test.sh --scope spain --include-performance`) is only run on demand, when asked: never on your own initiative. It measures what only shows up at country scale and what depends on the machine (latency, throughput, accuracy under load). It compares itself with the last pushed commit: it measures that commit's baseline when the commit or the data change, and it measures load on both servers at once, in turns (PROJECT.md §20). Never compare timings with a measurement from another time: on this machine they vary more than any change. If something gets worse, measure the changes of the batch separately to find the culprit.
- **The engine is generic: it must work the same with Spain, France, Germany, Chile or any other country and data source.** That it is tested with Spain today does not justify any Spain-specific fix.
  - No merge, ranking, parsing or normalization fix is based on names, languages, codes or specific cases of a country ("Aliseda", "Sant", "Calle Real", Catalan-Spanish…). It is based on general properties of the data: entity type, administrative hierarchy, importance, distance, sources and multilingual names.
  - Country-specific data (street-type dictionary, partitions…) goes in its country pack, as data and not as logic. Even better if it is extracted from the sources themselves (e.g. equivalences between languages, from OSM's `name:*` names), so it works for any country without writing it.
  - Before a fix, ask yourself: would it work the same with the data of France or Chile? If not, it is not the fix.
- One conformance suite per port (`crates/geko-conformance`). A new provider runs it from `tests/conformance.rs`.
- Every new source declares its license in the provider and in the bundle manifest.
- Licenses (PROJECT.md §6.4): the code is AGPL-3.0-only (`LICENSE`) and every outside contribution requires the CLA (`CLA.md`). While the repository stays private, the ODbL is complied with by offering the method of the derived database. Any change to the sources or to the merge rules updates `docs/FUSION_METHOD.md`, which serves `/geocoder/v1/attribution/method`.

## Optimizations: what worked and what did not

Before optimizing, check this list so as not to repeat what was already discarded. When you try something, add it here with its measurement, whether it works or not. Always measure A/B in the same batch (the machine's performance varies between batches) and with all of Spain: some costs only show up at country scale.

**Method that works:**
- To find a memory peak, put probes per phase (`VmRSS` and `VmHWM` from `/proc/self/status`) before assuming the cause. With the index builder, the suspect (the word index) was not the problem.
- For latency, get the list of the slowest requests with the server's `timing_us`. Then `geko geocoder query "<query>" --autocomplete --debug` gives the time of each reading of the query. It does not apply the time budget: it measures each reading in full.
- Before accepting a baseline with `GEKO_GOLDEN_UPDATE=1`, review the data table of the report (`entities …`: baseline, then now). A normalization change split «Ma - 15» and «Ma-15» into two streets and added 1,777 duplicate addresses in the Balearic Islands, and it was accepted without noticing (2026-10-18).
- After a large build (the whole `ci/test.sh`, `--force`), the WSL disk cache is empty and the first golden shows medians in milliseconds: the mapped index is read from disk. Repeat the golden on its own before blaming the code; instruction counts (valgrind) do not depend on that.
- Measure accuracy at rest and with 16 concurrent requests. Use the Spain sets, the Balearic golden and the keystrokes of `geko-eval keystrokes`. Compare queries one by one between the old and the new version, not just the percentages.

**Worked:**
- Index builder memory (2026-10-16): Spain's peak from 8.0 to 2.9 GB, with a byte-identical segment. Each entity stores its properties as a compact JSON fragment, not as a `serde_json::Map`. Its names go in a single string, not in a `Vec<String>`. The canonical data is read batch by batch and the cold part is written to disk as it is generated (`BlobWriter`).
- Merge by province and a columnar index builder, without one object per address (BACKLOG 6, 6e).
- Index builder time (2026-10-16, BACKLOG 9): from 136 to 75 s with Spain, with an identical segment. The expensive part was not normalizing names (parallelizing it only gained 10 s), but inserting millions of text keys into a `BTreeMap`: they are now accumulated in a `HashMap` and sorted once. Parsing and the cold part run in parallel by blocks and are merged in id order.
- Distributing records to the partition that contains them (2026-10-16, BACKLOG 6f): the stage costs 4.2 s with Spain (16 M points), because `PreparedArea` already splits edges into bands and almost every point is resolved with its own partition. A separate grid was not needed.
- Reverse memory and time (2026-10-18, BACKLOG 32): Spain's peak from 6.0 to 1.7 GB and from 92 to 9.8 s, with byte-identical output. It read whole canonical tables, with all their columns; it now reads only those it uses (`ProjectionMask`), batch by batch. Before reading a whole Parquet file, check which columns are needed.
- Time of the cross-source POI merge (2026-10-19), with Overture in Spain: from 451 to 7 s summing the 52 provinces, and the whole merge from 346 to 186 s, with byte-identical canonical data. It looked for nearby OSM POIs in 1 km cells and compared each pair of names with three `format!`. It now uses 110 m cells, equally wide in meters at any latitude, and compares without creating strings. Put timing probes per phase (`elapsed` in each `tracing::info!`) before assuming the cause.
- Cross-source POI merge without visible errors (2026-10-19), reviewing by hand samples of the new merges and the old ones, not just counting them: the duplicate metrics do not see wrong merges. Samples of 60 to 100 with Spain:
  - One name inside the other failed 3 out of 60 («Fátima», taxis, with the Fátima parish): it now requires the same kind of place, learned from equal names.
  - One rare word in common, nothing more (14,400 merges): 8 out of 60 wrong, and 3 out of 60 even requiring it to be rare in the whole province. Discarded.
  - The same phone or website, nothing more: 9 out of 30 wrong (a hotel and its restaurant share a website). The same address: useless. A rarely repeated phone or website, plus one rare word in common and the same category key: 0 clear errors in 80 (7,000 merges).
- Hilbert-packed, mapped reverse index, instead of an R-tree built in RAM on load (BACKLOG 4).
- Response cache (2026-10-18): with Spain and the real keystrokes, 74 % hits and, with 16 concurrent, autocomplete throughput from about 4,000 to about 10,000 QPS and p99 from 15–16 to 11 ms. Off by default in the code, to measure the engine.
- Kilometer points and road codes (2026-10-18): «A-7» was split into the article «a» and the number 7. Joining letter, hyphen and digits into one word when folding, and preferring the street that has the requested number, resolved «N-340 km 1050» correctly, Spain's control 90.2 → 90.5 % and +91 keystrokes. When folding, do not copy the text into a vector: doing so raised parsing instructions by 5 %; looking at the next byte costs nothing.
- Half-typed postcode (2026-10-18): a lone number, while typing, also looks for the postcodes that start with it (before, postcode entities were only reached with the full postcode). Spain's postcode keystrokes: top-1 33.8 → 39.0 % and top-5 34.0 → 53.2 %, with no losses.
- Half-typed locality (2026-10-18): a hamlet named exactly like the prefix («Sarri», «Pila») no longer hides the municipalities that start that way (Sarria, Pilas), and a «locality only» result of one reading no longer ranks ahead of a full match of another. Spain's keystrokes: top-1 28.7 → 32.2 % and top-5 37.3 → 38.2 %, with no category getting worse and the same instruction counts. Always expanding the prefix, even when it matched a municipality, gave almost the same (32.2 %) with 8 % more instructions.
- Autocomplete with locality and with typos (2026-10-19), measured with Spain: 13 keystrokes gained and none lost, full queries unchanged.
  - A result that only matches after dropping a word of the query (relaxation) or through another of its names ranks below the best one that matches the whole query in a municipality named exactly like the locality another reading read, if it is from another municipality: «manolo bakes barcelona» gave the ones in Madrid, and «carrefour express barcelona» the one in Madrid that Overture calls «… Ciudad de Barcelona, 142». The rule also weighs when deciding who enters the top, not only when sorting. Without the condition of a municipality with that name, «palma de mallorca» gave «via Palma» in Manacor (Mallorca is an island with places, not a municipality) and lowered the confidence of hits; with it, 13 keystrokes are gained instead of 58, without that risk. Without the one of a reading with locality, a weak full match («Calle Manolo Millares») sank the good ones.
  - The word being typed, if no word starts that way and it has 5 letters or more, is also read with a typo in its beginning (`fuzzy_prefix`, one edit up to 7 letters and two from 8), in addition to as a whole word with a typo: «Plaza Vicente Aleixn».
- Search and autocomplete latency (BACKLOG 8):
  - A typo is not expanded to words present in more than 2 % of the index.
  - Typos and relaxation only run while there is no complete answer.
  - A 1–2 letter prefix, or one whose expansion exceeds 0.5 % of the index, is checked against the names instead of being intersected.
  - The typo automaton comes from `levenshtein_automata`, not from `fst`'s, which cost about 30 ms per long word.
  - Search and autocomplete run in a pool bounded to one per core.
  - Time budget per query.
- More latency (2026-10-16), without changing accuracy at rest:
  - The time budget also cuts secondary readings halfway through, checking the clock every 128 candidates. Before, it was only checked between readings, and a secondary reading started in time could take 20 ms.
  - The query's postcode is looked up in the manifest only once, not for each candidate street: it was a linear search among 10,931 postcodes. An address with a postcode went from 14 ms to 84 µs.
  - The typo retry does not expand a word that exists as is and is among the most common (its list exceeds 0.5 % of the index, like «santa» or «maria»): it joined lists of hundreds of thousands of entities.
  - Result with Spain, on the server: autocomplete p99 from 8.7 to 5.6 ms and search p99 from 7.6 to 4.0 ms. With 16 concurrent, autocomplete p99 drops from 19.7 to 16.5 ms and search from 20.8 to 13.9 ms.
- Locality resolution (2026-10-16), with identical results without budget (0 differences in 17,829 keystrokes and 2,006 Spain queries):
  - When resolving the locality by its words, it filters by entity type before checking the prefix in the name, which requires normalizing it. Localities that start with a very common word («de Santa», «a Jo») walked thousands of streets and POIs normalizing each name. «Igrexa de Santa» went from 8.4 to 3.7 ms.
  - Each locality is resolved once per query: the place and address readings usually share the locality text.

**Did not work (do not repeat):**
- Lowering the autocomplete budget to lower its p99 (2026-10-16). The p99 stays pinned at the budget: expensive queries are cut right there, and making their readings cheaper only lets more fit before the cut. Each millisecond less costs about 0.7 points of top-5 in the keystrokes (5 ms: 35.5 %; 4 ms: 34.7 %; 3 ms: 34.5 %; no budget: 36.3 %). Setting the budget is a product decision, not an optimization.
- Measuring half a millisecond on the development machine: with Docker and the browser open, batches vary ±20 %. Latency goals need the reference hardware or, at least, the server pinned to 4 cores (`taskset -c 0-3`) and the client on the others, with interleaved A/B measurements.
- Also reading each address as a street name (BACKLOG 3b): it multiplied address latency by 5.
- Retrying with typos at distance 1, instead of 2, the words that exist in the index (2026-10-16). It loses transpositions, which cost two edits and often form words that exist somewhere («Ilgesia», «Francsico», «Moartín»). Spain's addresses with typos dropped from 96 to 90 %.
- Not treating the last word of the street as a prefix when a locality follows it (2026-10-16). Without a comma, the parser also reads the end of the street as a locality («Calle C» + «Soldevil»). The street, already complete, then wins with the exact-name bonus. It lowered top-1 in three keystroke categories. The slow case that motivated it is already solved by the budget within the walk.
- A fixed list of Catalan-Spanish equivalences in the code (BACKLOG 11): it is not generic. Equivalences must come from the data.
- Indexing the learned equivalences between languages (2026-10-16, BACKLOG 11), as words or as translated names. The lists of common words grew («sant» with all the «san»), and the right street fell outside the candidate cap: 278 keystrokes changed and Spain's addresses with postcode dropped (90 → 88 %). Translating whenever there was no exact name did not work either: while typing there almost never is one, and the translations overtook the literal ones. Translation happens at query time, only as a fallback (PROJECT.md §9.5).
- More exact-name bonus while typing when the last word is already a whole word of the index (2026-10-19): with 0.15 instead of 0.05, 72 keystrokes lost and 27 gained, and full autocomplete queries dropped; with 0.3, worse.
- Reading the word being typed with a typo also when its prefix has only 3 entities or fewer (2026-10-19), for «famlia», which has one with that same typo: 38 keystrokes lost and 19 gained. Rare but real names («Amatitá», «Regència», «Arnea») were confused with common words. Only when no word starts that way.
- Linking words and POI fame while typing (2026-10-18, BACKLOG 13): removing «de», «la»… from the query, or raising the affinity of famous POIs, also while typing changed 44 of Spain's keystrokes for the worse (municipalities and POIs). Only in full search.
- Raising the weight of POI fame from 0.4 to 0.6 (2026-10-17, BACKLOG 13). It fixed none of the famous ones that fail («alhambra», «aeropuerto de barajas», «estación de atocha»: the text sinks them, not the importance) and lowered top-1 for POI keystrokes (42.2 → 42.0 %) and for streets.
- Separating by distance same-name streets with repeated numbers (BACKLOG 4c): only 9 suffixes dropped and the duplicate-street metric went up.
- A ×1.5 latency tolerance in `geko-eval check`: it fails from noise. ×2 and +1 ms are used.
- Autocomplete precomputed per H3 cell and `admin_cells` (2026-10-18, BACKLOG 10): not needed. A 2–3 letter prefix already takes 43–108 µs with Spain and the focus already biases it; reverse, 0.2–0.3 ms. It would save less than 0.1 ms with a budget of 5.
- Reading only the needed columns in the index builder too (2026-10-18), as in reverse (BACKLOG 32). With Spain, interleaved A/B: 79.3 and 73.2 s before, 71.4 and 76.3 s after, with the same peak (2.84–2.88 GB). The index uses almost every column, and the geometries it skipped weigh little. Same files.

**Known cost:** with the time budget, secondary readings are cut when it runs out. If the right answer came from one of them and the query is expensive, it is lost. At rest it happens in a few keystrokes: 4 of 2,692 street ones fall out of the top-5. Under load, in a few more cases. It is the budget's trade-off, which is tuned in `[serve]` and disabled with 0.
